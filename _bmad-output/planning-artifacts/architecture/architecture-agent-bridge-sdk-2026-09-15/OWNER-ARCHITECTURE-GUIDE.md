# AgentBridge AA-1 — руководство владельца

## Статус, принятое решение и следующий шаг

Мы не выбрали язык программирования и ещё не проектируем отдельные сообщения протокола. Сначала мы зафиксировали «конституцию» AgentBridge — правила, которые не позволят будущим частям проекта противоречить друг другу или незаметно ослабить безопасность.

Главный результат: AgentBridge проектируется как **самостоятельный Native-протокол**, а не как обязательная надстройка над MCP, A2A или другими решениями. Совместимость с ними позднее может обеспечиваться необязательными Bridges.

Project Owner принял AD-1, AD-2, AD-3, строгую поправку AD-3A и финальный пакет AA-1. Все обязательные внутренние reviews завершились PASS, blockers закрыты, а AA-1 Gate пройден. Следующим шагом разрешено только документальное проектирование AA-2.

## Что разрешено и что запрещено сейчас

### Разрешено сейчас

- исправлять и проверять документальный пакет AA-1;
- готовить текстовые схемы, определения, proof obligations и планы проверки;
- после положительного AA-1 Gate вести **документальное проектирование AA-2**: описывать роли, полномочия, состояния, переходы и ошибки без запуска модели и без создания reference code;
- изучать существующие протоколы как источники механизмов, дефектов и будущих необязательных Bridges.

### Не разрешено сейчас

- запускать executable model или prototype без отдельного AD-21 Pre-Prototype Control Manifest для конкретного запуска; этот экземпляр должен быть заполнен, независимо проверен, подписан, ограничен сроком действия и иметь статус `frozen-approved`;
- начинать reference implementation до прохождения AA-6; disposable prototype не становится reference implementation и не получает compatibility promise;
- использовать production/customer/personal/regulatory data, production credentials или выполнять реальные consequential effects;
- тратить деньги, заключать внешние договоры, регистрировать компанию/фонд/marks, передавать protocol assets или публично использовать бренд без отдельного разрешения;
- публиковать пакет либо делать публичные claims `secure`, `production-ready`, `industry standard` или claims об adoption без соответствующего Gate и отдельной авторизации.

Документ AA-2 и executable model — не одно и то же. Текстовую модель можно проектировать в разрешённом Gate scope; её запуск является executable work и всегда требует конкретного frozen-approved AD-21, даже если код одноразовый и не предназначен для production.

## Архитектура одним образом

Представьте песочные часы:

- сверху находятся разные агенты, компании, сервисы и отрасли;
- снизу — разные сети, форматы, языки, системы идентификации и инфраструктура;
- узкая середина — единый смысл AgentBridge, который все понимают одинаково.

Эта середина называется **Core**. Она небольшая не потому, что из неё убрали важное, а потому, что в ней оставлено только действительно универсальное. При этом Core должен полностью охватывать общие правила полномочий, действий, эффектов, ошибок и доказательств.

## Из каких частей состоит AgentBridge

| Часть | Простое значение |
| --- | --- |
| Core | Универсальные правила безопасного взаимодействия. |
| Profile | Более строгие правила для конкретного класса применения. |
| Extension | Дополнительная явно согласованная возможность. |
| Binding | Способ передать смысл AgentBridge через конкретную сеть, формат и криптографию. |
| Bridge | Необязательный перевод между AgentBridge и другим протоколом. |
| External System | Заменяемая внешняя система идентификации, политики, поиска, платежа или хранения. |
| SDK | Удобный код для разработчиков, но не источник правил протокола. |
| Conformance | Независимые проверки того, что реализация действительно соблюдает спецификацию. |

Ни одна из частей за пределами Core не может изменить его смысл. Если транспорт сообщил «доставлено», это ещё не означает «покупка совершена». Если сообщение подписано, это подтверждает источник утверждения, но не обязательно истинность внешнего факта.

## Что означает «полный, но ограниченный v0.x»

Первая архитектурная версия должна заранее учитывать основные направления будущего агентного интернета:

- агент ↔ сервис компании;
- агент ↔ агент;
- backend ↔ backend / B2B;
- асинхронные и обратные взаимодействия;
- делегирование;
- взаимодействие нескольких сторон.

Но мы не будем сразу создавать банки, магазины, платежную сеть, глобальный каталог или десятки транспортов. Для проверки Core достаточно двух первых Profiles:

1. безопасный обмен информацией;
2. действие, способное вызвать внешнее последствие.

Такой подход оставляет фундамент готовым к будущему, но сохраняет проект конечным и проверяемым.

Для более строгой практической проверки на этапе AA-7 дополнительно используют второй экспериментальный Native Binding, два несвязанных тестовых домена, два Extensions и два необязательных Bridges к разным внешним протокольным моделям. Это позволяет попытаться обнаружить скрытую привязку Core к первому транспорту, домену или чужому протоколу. Успешный результат относится только к точно проверенной матрице и не доказывает универсальность для всех будущих случаев. Обязательным Base Binding остаётся один, а Bridges не входят в Native Path.

## Главные неприкосновенные правила

- Найти сервис или узнать его возможности — не значит получить право действовать.
- Установить личность — не значит автоматически получить полномочия.
- Доставка сообщения — не значит, что внешнее действие произошло.
- Неизвестный результат нельзя называть успехом или отсутствием эффекта.
- Делегирование может только сужать полномочия, но не расширять их.
- Отмена не стирает уже произошедшее действие; компенсация является новым действием.
- Повтор сообщения не должен создавать повторный внешний эффект в гарантируемой области.
- Неизвестная критическая функция, потеря смысла или downgrade приводят к безопасной остановке.
- Никакой AgentBridge Cloud, коммерческий SDK или Bridge не обязателен для базового Native-взаимодействия.
- Reference implementation не определяет норму: норма находится в спецификации и независимо проверяется.

## Как будет измеряться качество

Для запретных исходов действует нулевая терпимость:

- запрещённые действия или раскрытия — 0;
- расширение полномочий — 0;
- превращение `unknown` в успех — 0;
- скрытые обязательные коммерческие или центральные зависимости — 0;
- критические переходы без способа проверки — 0.

Точные значения скорости, размера сообщений, времени ожидания и потребления памяти сейчас не выдумываются. Они будут установлены после появления модели нагрузки и кандидатов Native Binding. Это защищает проект от красивых, но необоснованных обещаний.

## Что это решение пока не утверждает

- Rust, Go или другой язык;
- конкретный транспорт, формат сообщений или криптографию;
- готовность к production;
- доказанную скорость и масштабируемость реального кода;
- полную совместимость независимых реализаций;
- первый коммерческий рынок;
- принятие индустрией или статус стандарта.

Эти решения имеют отдельные этапы и доказательства. В частности, выбор Rust остаётся гипотезой.

## Как понимать будущие этапы

| Этап | Простой результат |
| --- | --- |
| AA-1 | Зафиксирована конституция, границы и измеримая планка качества. |
| AA-2 | Однозначно описано, как протокол понимает стороны, полномочия, действия, состояния и эффекты. |
| AA-3 | Спроектирована защита от атак, утечек, компрометации и ошибок доверия. |
| AA-4 | На основании контролируемых исследований выбран первый Native Binding и технический baseline. |
| AA-5 | Созданы независимые способы проверки любой реализации. |
| AA-6 | Архитектура собрана в согласованную версию v0.x и разрешён ограниченный non-production implementation scope. |
| AA-7 | Две независимые реализации проверяют совместимость, устойчивость и производительность по точно зафиксированной матрице Bindings, доменов, Extensions и Bridges; результат может поддержать или опровергнуть только ограниченный claim. |

## Граница результата AA-1

AA-1 не говорит, что протокол уже спроектирован целиком. Он говорит, что установлен правильный фундамент, а следующие архитектурные решения обязаны оставаться внутри него.

После AA-1 Gate PASS следующим шагом является **AA-2 — Abstract Normative Model**: точная логическая модель ролей, полномочий, действий, состояний, эффектов и доказательств. Документальная часть AA-2 разрешена; запуск любой исполнимой модели требует отдельного frozen-approved AD-21, а reference implementation остаётся запрещённой до AA-6.
